# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Cause grounded in repro | The plan's Diagnosis, read against the repro-evidence block's steps, control runs, and debug output | The stated cause is consistent with every observation in the repro evidence. FAIL if any control run, isolating step, or debug output in the repro evidence rules the stated cause out (for example: the failure still happens with the blamed component absent, or the blamed component demonstrably works in a control), or if the plan ignores the evidence and asserts a cause it does not cite. A plan that names the same component the repro isolates passes. | required |
| One bounded change | The plan's Scope statement, Files list, and Approach, read against the issue's actual ask | The plan is one change that fixes the reported behavior: it names what is in scope and the work listed matches it. FAIL if the Approach or Files include work the issue did not ask for: refactors or rewrites of surrounding code, migrations or dependency swaps, new options or settings, UI or docs overhauls, new frameworks, or several independent fixes bundled together, even when the core fix is correct and the language is confident. Deferring extra work explicitly (a not-in-scope line, a follow-up) is bounded and passes. | required |
| Fixes the cause, not a workaround | The plan's Approach read against the issue and the thread's maintainer signals | The change addresses the reported defect itself. FAIL if the plan only documents, wraps, or works around the symptom (for example docs-only or an FAQ entry) when the issue or thread has isolated a code culprit or the maintainer asked for a code fix. | required |
| Stranger could start | The plan's Files, Approach, and Diagnosis | A stranger could begin work without asking the author: the plan names the concrete files or areas, and the chosen approach (one approach, not a menu). FAIL if the plan defers the real decisions to build time ("somewhere", "whichever is easier", "investigate first", "not sure which layer"), names no files, or is only intent. Terse is fine if the file, the change, and the approach are all named. | required |
| Decisive test plan | The plan's Test plan, read against the repro-evidence steps | The test plan names an observable outcome for the fix itself, tied to the repro: a specific command or input to re-run and the expected result (output, exit code, or a regression test that fails before and passes after). FAIL if the test plan is vague ("should feel fast", "nothing else should break") or only a generic suite run ("run the full test suite") with no observable outcome for this fix. | required |
| Unknowns stated honestly | The plan's Approach, Test plan, and comment, read against the repro evidence | Anything the plan has not verified is named as unverified or an open question, and nothing is asserted as certain that the evidence does not show. FAIL if the plan claims results it could not have (verified behavior the repro does not show, a confident root cause with no evidence). Naming an unknown and how it will be checked passes. | preferred |
| Engages the thread | The plan comment, read against the Thread highlights (maintainer or owner direction, prior PRs, prior art) | The comment is consistent with explicit direction in the thread: if a maintainer stated the cause, the direction, or asked for something, the comment follows or engages it; if open PRs or prior art exist, the comment acknowledges them rather than racing or ignoring them. FAIL if the comment ignores or contradicts explicit maintainer direction in the thread highlights, or duplicates an open PR without mentioning it. A thread with no direction to engage passes. | required |
| Repo conventions and AI policy | The plan comment, read against the repo-facts block (contribution policy and bug-report template asks) | The comment complies with what the repo-facts block states. Every package is treated as AI-assisted work. If the contribution policy requires disclosing AI use (tool and extent), the comment must contain that disclosure. If the policy requires comments to be in the human's own words, the comment must read as the contributor's own and may say so. FAIL if a stated disclosure or voice requirement is missing from the comment. A policy that states no AI policy, or no ask for issue comments, passes. | required |
| Comment matches the plan | The plan comment read against the candidate plan | The comment states the same approach, scope, and test as the plan, and does not promise more than the plan commits to. FAIL if the comment contradicts the plan or promises a wider change than the plan scopes. | required |

## Verdict rule

Accept only if every `required` check passes. Reject if any `required` check is `fail`. `unclear` on a `required` check counts as `fail`: a plan whose readiness cannot be verified from the package is held. `preferred` checks are reported in the output but never change the verdict.
